# 🚌 Smart Bus Management System (ESP32-S3 + Arduino UNO + 4 AI Agents)

An **AI-Assisted Multi-Bus Smart Transit Management Platform** combining real physical IoT edge hardware (**Bus SB-101**), autonomous multi-bus software simulation (**Buses SB-102, SB-103, SB-104**), computer vision (**YOLOv8 Nano & Driver Drowsiness Detection**), **4 Autonomous Intelligent Agents** (Passenger, Safety, Fleet, Maintenance), and dual web applications (Admin Operations Command Center & Passenger Mobile Web App).

---

## ⚠️ 1. Real-World Hardware Architecture & Physical Constraints

### Physical Bus (Single Real Unit): `SB-101`
Only **Bus SB-101** contains physical IoT hardware.

```
                 REAL BUS SB-101
                       │
          ┌────────────┴────────────┐
          │                         │
      ESP32-S3                  Arduino UNO
          │                         │
   GPS / Dual IR / Camera       RFID / 16x2 LCD
   WiFi / Telemetry Dispatch    LEDs / Active Buzzer
          │                         │
          └─────── UART Serial ─────┘
          (COUNT:n, ALERT:type, LED:color, BUZZER:state, LCD:msg, RFID:uid)
                       │
                     Wi-Fi
                       │
                 Flask Backend
```

#### ESP32-S3 Master Edge Controller (`esp32_s3/smart_bus_esp32_s3.ino`)
- **GPS (NEO-6M UART)**: Real-time latitude, longitude, speed, heading, altitude.
- **Dual Optical IR Sensors (GPIO 4 / 5)**: Hardware interrupt state machine tracking passenger entry & exit.
- **OV3660 Camera**: Onboard cabin surveillance and passenger counting frames.
- **Wi-Fi Communication**: Real-time REST API JSON telemetry transmission to Flask backend.
- **Inter-Controller UART Link (Serial1)**: Relays RFID tag scans from Arduino UNO and transmits actuator commands.
- **Emergency SOS Push Button (GPIO 21)**: Hardware interrupt trigger.

#### Arduino UNO Companion Controller (`esp32_s3/arduino_uno/smart_bus_arduino_uno.ino`)
- **RC522 RFID Reader (SPI)**: Reads passenger digital fare smart cards and depot/stop marker tags.
- **I2C 16x2 / 20x4 LCD Display (0x27)**: Onboard real-time HUD displaying occupancy, bus status, and safety alerts.
- **Status LEDs (Green & Red)**: Visual alert indicators.
- **Active Piezo Buzzer**: Audible RFID scan beeps and high-decibel emergency siren.
- **Non-blocking UART Serial Message Parser**:
  - `COUNT:<n>` -> Updates displayed passenger count
  - `ALERT:<type>` -> Triggers visual/audible alert state (e.g., `OVERCROWDED`, `DROWSINESS`, `SOS`, `OK`)
  - `LED:<color>` -> Sets `RED`, `GREEN`, `BOTH`, or `OFF`
  - `BUZZER:<state>` -> `ON`, `OFF`, `BEEP`
  - `LCD:<msg>` -> Displays custom status message
  - `RFID:<uid>` -> Sends scanned UID back to ESP32

## 🏷️ 2. Physical Sensor Limitations & Explicit Data Source Tagging

### No Fake Physical Sensor Readings
Physical sensors for **Battery ADC voltage**, **Engine temperature**, and **Tire pressure** are **NOT physically connected**.

The platform provides **Manual Maintenance Data Entry** via the Admin UI.
- All vehicle health metrics are explicitly tagged in the database, API, and UI as:
  - `MANUAL` / `Admin Entered` (when submitted by maintenance staff)
  - `SIMULATED` (when generated by the multi-bus simulator)
- Sensor data is **never claimed as ESP32 physical sensor measurements**.

### Fleet Data Source Matrix

| Bus Identifier | Hardware Available | GPS Source | Passenger Source | Camera Feed | Maintenance Data Source | Bus Type |
|---|---|---|---|---|---|---|
| **SB-101** | `true` (ESP32-S3 + UNO) | `REAL` | `REAL` (IR + YOLO) | `ONLINE` (OV3660) | `MANUAL` / Admin Entered | Physical IoT Demo Unit |
| **SB-102** | `false` | `SIMULATED` | `SIMULATED` | `NOT AVAILABLE` | `MANUAL` / Admin Entered | Software Simulated Bus |
| **SB-103** | `false` | `SIMULATED` | `SIMULATED` | `NOT AVAILABLE` | `MANUAL` / Admin Entered | Software Simulated Bus |
| **SB-104** | `false` | `SIMULATED` | `SIMULATED` | `NOT AVAILABLE` | `MANUAL` / Admin Entered | Software Simulated Bus |

## 👥 3. Passenger Counting & Reconciliation Engine

The system implements two levels of passenger occupancy determination for **Bus SB-101**:

1. **Level 1 -- Physical Optical IR Counter**:
   - Directional optical IR sensors mounted at entrance/exit doors.
   - Real-time interrupt counting on ESP32-S3 with 350ms hardware debouncing.
2. **Level 2 -- YOLOv8 Nano Computer Vision**:
   - Lightweight `yolov8n` person detection and centroid tracking across video frames.
   - Line-crossing algorithm preventing double-counting across consecutive frames.
3. **Multi-Sensor Reconciliation Strategy**:
   - Configurable per bus via database:
     - `IR_PRIMARY` (Default): IR counter acts as primary ground truth, YOLO provides visual verification.
     - `YOLO_PRIMARY`: YOLO computer vision count acts as primary.
     - `HYBRID`: Weighted combination ($0.65 \times \text{IR} + 0.35 \times \text{YOLO}$).

## 👁️ 4. Camera Roles & Driver Face Recognition Studio

### Camera Separation Architecture:
1. **ESP32-S3 OV3660 Onboard Camera**: Strictly dedicated to **Passenger Counting** and YOLOv8n occupancy centroid tracking on Bus SB-101.
2. **On-Demand Driver Face Recognition Studio** (`frontend/admin/driver-recognition.html`):
   - Opens when the Admin clicks to inspect a driver's face & attentiveness state.
   - Utilizes live Admin Webcam (`getUserMedia`) or 68-point facial landmark simulator.
   - Computes real-time **Eye Aspect Ratio (EAR)**:
     - $\text{EAR} \ge 0.25$: Driver is **ACTIVE** (e.g., Bus SB-101 driver Michael Vance, EAR: 0.32, 96% score).
     - $\text{EAR} < 0.22$: Driver is **SLIGHT SLEEPY** / Drowsy (e.g., Bus SB-102 driver David Miller, EAR: 0.18, 48% score).
   - On drowsiness detection, dispatches immediate Safety Agent escalation and hardware actuation to SB-101 (`LED:RED`, `BUZZER:ON`, `LCD:DROWSY DRIVER`).

```
Admin clicks "Inspect Driver Face"
               │
               ▼
Driver Face Recognition Studio (Window / HUD)
               │
   ┌───────────┴───────────┐
   ▼                       ▼
Bus SB-101 (Active)     Bus SB-102 (Slight Sleepy)
EAR = 0.32 (Nominal)    EAR = 0.18 (Prolonged Eye Closure)
Attentive: 96%          Safety Agent Alert Triggered
               │                       │
               ▼                       ▼
      Standard Log           Hardware Alarm (SB-101)
                             + Admin Siren Broadcast
```

## 🧠 5. Four Autonomous Intelligent Agent Architecture

```
                       AGENT SYSTEM
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
  Passenger Agent      Safety Agent        Fleet Agent
  (Chatbot, ETA,      (SOS, Drowsy,      (Headways, Realloc,
   Search, Seats)      Overcrowd)         Standby Swap)
        │                   │                   │
        └───────────────────┼───────────────────┘
                            │
                            ▼
                    Maintenance Agent
                    (Rule Engine & ML RUL)
```

1. **Passenger Agent (`agents/passenger_agent.py` & `backend/services/passenger_service.py`)**:
   - Dynamic real-time ETA calculation combining Haversine distance, speed, congestion, and dwell times.
   - Origin-destination optimal route search with live fares.
   - Geolocation nearby transit stop finder with walking time.
   - Natural Language Processing (NLP) Transit Chatbot (`/api/chatbot/message`).
   - 2D Visual Seat Layout engine (modeling accessible, window, and aisle seating).

2. **Safety Agent (`agents/safety_agent.py` & `backend/services/safety_service.py`)**:
   - Severity classification: `INFO`, `WARNING`, `HIGH`, `CRITICAL`.
   - Overcrowding detection (>80% Warning, >100% Critical).
   - Speed limit violation monitor (>65 km/h).
   - Hardware Emergency SOS button escalation and siren dispatch.
   - Driver drowsiness event ingestion with automated edge actuation.
   - Dynamic fleet and driver safety index calculation.

3. **Fleet Agent (`agents/fleet_agent.py` & `backend/services/fleet_service.py`)**:
   - Route deviation & geofence cross-track calculator (>350m alerts).
   - Headway regulation and bus bunching prevention across both real and simulated buses.
   - **Autonomous Standby Bus Swap**: Automatically replaces a degraded bus with a healthy depot standby unit with zero manual dispatcher calculation.

4. **Maintenance Agent (`agents/maintenance_agent.py` & `backend/services/maintenance_service.py`)**:
   - **Rule-Based Maintenance Priority Engine**: Analyzes admin-entered manual maintenance data and orders fleet maintenance priorities:
     $$\text{CRITICAL} \longrightarrow \text{SERVICE\_REQUIRED} \longrightarrow \text{MONITOR} \longrightarrow \text{NORMAL}$$
   - **ML Predictive Degradation (LSTM RUL Model)**: Estimates Remaining Useful Life (in days) and predicted component failure dates.
   - Automated workshop work orders and service resetting.
